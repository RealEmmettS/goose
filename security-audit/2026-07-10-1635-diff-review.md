## Security posture overview

1. **What leaves the machine:** only release-manifest/artifact requests to the project's GitHub
   release origin and normal OS network metadata. There is no telemetry, analytics, account,
   advertising, or user-media upload path.
2. **What is stored:** versioned TOML configuration, an owned install receipt, optional autostart
   state, and user-supplied notes/images. No password, token, financial, health, or identity data
   is accepted. Mutable media stays in per-user data directories, outside executables, MSI-owned
   directories, and the sealed macOS bundle.
3. **Who can access it:** normal filesystem ownership governs config/media. Unix IPC uses a
   UID-owned `0700` directory, `0600` socket, and peer credentials. The Windows pipe rejects
   remote clients and grants only the current user SID and SYSTEM.
4. **Retention and deletion:** ordinary uninstall preserves user media; explicit purge handles
   user content through the documented backup/removal path. Installer-owned aliases, desktop
   entries, PATH blocks, receipts, and autostart integrations are removed only after ownership is
   proven. No server-side retention exists.

## Fixed during review

### S-01 — Mutable or unverified release-build executables

- Severity: HIGH
- Confidence before fix: 0.95
- Area: `.github/workflows/release.yml`, `macos-packaging.yml`, and
  `windows-installers.yml`
- Attack path: a mutable third-party action/container or an unverified pipe-to-shell cargo-dist
  installer could alter binaries produced by the trusted release workflow.
- Resolution: pinned the third-party Rust action to a commit, pinned cargo-xwin's container by
  digest and package version, replaced cargo-dist installer pipes with exact-version archives and
  hard-coded SHA-256 checks, restricted workflow permissions, and kept publication in one
  write-scoped final job.
- Verification: workflow contract tests, `actionlint`, exact hash checks in workflow source, and
  the no-pipe/no-mutable-tool regression assertions pass.

### S-02 — Elevated Windows helpers resolved executables through search order

- Severity: HIGH
- Confidence before fix: 0.94
- Area: `src/install.rs`, `src/update.rs`, `script/honk300-installer.ps1.in`
- Attack path: a bare `msiexec.exe` or PowerShell name could resolve to an attacker-controlled
  executable in the caller's working directory before a normal update/install UAC approval.
- Resolution: resolve the authoritative system directory with `GetSystemDirectoryW` in Rust and
  the .NET system-folder API in the bootstrap, require regular non-symlink/reparse-point system
  executables, and pass exact paths to hidden update/uninstall helpers and elevated MSI launches.
- Verification: focused Rust/template tests assert exact System32 paths and reject bare process
  names; Windows x64/ARM64 checks and the complete workspace suite pass.

### S-03 — Note prank launched bare Notepad from the caller's search path

- Severity: MEDIUM
- Confidence before fix: 0.91
- Area: `crates/honk-platform-windows/src/lib.rs`
- Attack path: starting honk300 from a directory containing a hostile `notepad.exe` could execute
  that file when a note prank began, even though typing itself was target-scoped UI Automation.
- Resolution: resolve and validate System32 Notepad with `GetSystemDirectoryW`; never use a bare
  executable name. UI Automation remains the only typing path and there is no global-input
  fallback.
- Verification: the Windows backend test proves an absolute system path and target-scoped setter;
  all Windows tests pass.

## Integrity hardening completed

- The `honk300.release.v1` manifest now names each artifact's exact checksum sidecar. Manifest
  generation refuses a missing, symlinked, or mismatched sidecar, and the updater validates the
  exact `<artifact>.sha256` contract.
- Release inputs are exact stable tags and full commit IDs; every producer checks out that commit,
  all artifacts are collected before one draft upload, remote names/bytes are compared, and only
  then is the immutable release published as latest.
- Shell extraction rejects absolute/traversing/duplicate paths and links before extraction.
  Executable archive-attack tests cover tar and zip traversal, duplicates, and symlinks.
- Update artifacts are size/hash/reparse-checked again after the parent exits and before execution.
  Installed-version verification uses an owned exact executable path rather than `PATH`.
