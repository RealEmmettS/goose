TT;DR: Replace the detached Windows updater handoff and flat-payload replacement model with provenance-preserving, synchronous updates built around immutable release slots and stable aliases. Work is active; the board and repository were audited clean, and implementation starts with the receipt and installer contracts.

## Why
This is a direct operator order. `honk300 update` must behave like a modern CLI updater: remember how the current installation was obtained, reinstall through that same family/edition/track, keep public artifact names versionless, and return only after the resulting installation has been verified. A fresh installer is a separate expression of intent and may take over from another origin or intentionally install an older release.

Research compared Codex, Claude Code, uv, Deno, Velopack, Tauri, and Sparkle. The chosen design combines Codex-style immutable release slots and a stable `current` selector with package-owner delegation. The Network Diagnostics live-image retirement mechanism remains useful only for one-time legacy migration; uninstall-first cross-channel takeover is rejected because a later install failure can leave neither channel active.

## Plan
- Add ADR 0031, preserving ADR 0023's exact-tag integrity contract and superseding only ADR 0029's detached Windows transaction details.
- Extend the protected install receipt so installer family, edition, scope, release track, target, owned root, active release, and artifact identity are authoritative and backward-compatible with `honk300.install.v1`.
- Make `update --json` emit exactly one final object on stdout; route progress to stderr and return zero only after exact path/version/receipt/alias verification.
- Change Windows managed layouts to immutable `releases/<version>-<target>` payloads behind stable junctions. Keep the initiating old-slot process alive while a verified coordinator invokes the matching MSI/EXE/PowerShell path synchronously.
- Make fresh cross-channel installation stage and verify the new owner before activation and old-owner retirement. Preserve the new active install if cleanup becomes pending.
- Keep the universal DMG as fresh Mac transport while the managed app updates through the exact-tag signed app ZIP; keep Debian and shell origins distinct.
- Extend installer producers and disposable release jobs across Windows x64/ARM64, macOS universal2, Debian amd64/arm64, and GNU/musl shell targets.
- Synchronize the canonical plan, README, AGENTS/CLAUDE guidance, and both changelogs.

## Impact
Intended: update commands become synchronous and truthful, running Windows images are never replaced in place during ordinary updates, installer provenance is retained, fresh-install takeover is ordered safely, and stable public filenames remain compatible with `latest` discovery plus exact-tag payload verification.

Risks: installer component ownership, rollback, PATH/alias precedence, UAC handoff, legacy flat-layout migration, stale release cleanup, and cross-scope Windows registrations can regress uninstall or repair behavior. macOS bundle replacement must preserve signing, notarization, Accessibility identity, and the managed-path prompt boundary. Receipt migration must never bless foreign or reparse-controlled paths.

## Acceptance
All managed origins update only through their recorded family/edition/track. Windows updates retain the old process, activate and verify the new slot, and produce no scheduled-success false positive. Fresh takeover preserves old-active state before commit and new-active state after commit. Mac DMG, Debian, shell, and PowerShell paths remain isolated. Candidate, same-SHA main, and post-release workflows validate fresh public bytes and exact manifest identity.
