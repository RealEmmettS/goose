TT;DR: Let the Windows controller recognize its responsive settings window without requiring the input queue to become idle. Preserve exact companion verification, file leases, the ten-second deadline and failed-child cleanup.

## Why
After the approved v1.11.2 update, native entry-route verification repeatedly found loaded, responsive settings windows whose direct CLI controllers returned an initialization error. The instrumented original launcher records `WaitForInputIdle` returning `WAIT_TIMEOUT` with its exact child still alive. Start Menu and shortcut routes passed in the same observation. The idle predicate predates this update; the evidence does not identify a scrolling regression.

## Scope
Correct only Windows settings startup recognition and the package property required for its lease proof. Preserve all public commands, arguments, configuration, GUI behavior, rendering, installer ownership and the user's startup-off choice. Keep immutable v1.11.2 and earlier releases. Extended performance qualification remains deferred under the operator's instruction; #g14 remains the separate unresolved transparency investigation.

## Plan
Use one ten-second absolute deadline. Require the exact spawned child's visible, positive-area `NativeSdkWindowsHost` window to respond to a bounded `WM_NULL` request, then recheck identity and child liveness. Retain both verified files through that acknowledgement and kill/wait on failure. Require the accessibility DLL as a normal PE import. Qualify busy and failure fixtures, then the actual packaged entry routes before the existing complete release gates.

## Impact
The controller can return once its own settings message loop responds. A different process, hidden window, unresponsive child or incomplete payload cannot satisfy startup.

## Acceptance
Functional bar: explicit settings, bare command, application launcher and registered shortcut return successfully while their verified settings windows remain usable. Readiness recognition stays bounded and failed launches clean up their exact child while retaining verified file leases. Exceptional operating-system termination may extend the existing kill-and-wait cleanup; it must not release protection on a possibly live child to meet another deadline. Evidence bar: meaningful native fixtures, required local checks, all same-source candidate/main/publication gates, fresh-public downloads and approved installed verification. The repository owns platform/release gates; the operator owns Windows administrator approval.

The finite diagnostic checkpoint is complete: the original instrumented predicate timed out while the same child answered Windows messages. If the replacement still rejects that child, stop predicate expansion and inspect the first failed identity/response condition. Do not lengthen the timeout or accept visibility alone. Require three consecutive local rounds of all four candidate entry routes before freezing the source, using an isolated temporary shortcut for candidate shell activation. Verify the real registered shortcut again after approved public installation. Passing CI or a single retry does not replace these checks.
