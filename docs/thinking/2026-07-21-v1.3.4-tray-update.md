# v1.3.4 Tray Update Design Canvas

## Pre-flight

- Inputs: operator-approved plan, current v1.3.3 source, ADRs 0024/0028/0030/0031/0034/0037, native tray implementations, updater/lifecycle code, release workflows, and parallel platform investigations.
- Mode: critical-thinking self-check.
- Framework: Design.
- Exit target: a tested, provenance-preserving implementation and immutable global patch release.

## Empathize

The primary user is non-technical and already uses the native tray. Requiring them to discover a terminal command defeats that control surface. They need one obvious action, visible progress/authentication, automatic recovery/relaunch, and an ending state that cannot disappear before it is read.

## Define

Add one cross-platform `Update Honk300...` action without adding background traffic, a second updater, a settings model, or a persistent service. The running runtime must remain responsive until the updater's existing lifecycle transaction asks it to stop. Every install origin and exact-artifact verification remains authoritative.

## Research

- Running `update` synchronously on the runtime loop deadlocks because lifecycle ownership sends graceful Stop through that same loop.
- macOS Terminal and several Linux terminals allow user profiles to close or hold after child exit; auto-close cannot be assumed.
- The existing updater already provides exact-tag download, hash/size checks, origin preservation, lifecycle ownership, rollback, and post-install verification. Replacing it with Sparkle/Tauri or direct tray installer execution would weaken parity or duplicate security logic.
- Windows/macOS/Linux already have exact-executable terminal launch paths that can be extended with a fixed private helper argument.

## Ideate and converge

Considered: menu-open background checks; silent helpers with native notifications; visible terminal with automatic exit; terminal plus persisted result records; and a deliberately retained terminal helper. Chosen: an always-visible action and retained terminal helper. It has the smallest new trust boundary, supports existing UAC/sudo/package behavior, makes failures inspectable, and avoids terminal-profile races.

The playful no-op state will use exactly 100 curated messages. Randomness affects copy only; every rendered result pairs its flavor line with both fixed invariants: nothing required updating, and the window may be closed.

## Prototype contract

1. Native menu emits shared Update command.
2. Runtime launches the exact private helper in a terminal and continues ticking.
3. Helper acquires a separate one-at-a-time guard, then runs the existing managed updater.
4. Updater gracefully stops the runtime only when mutation requires it and retains lifecycle ownership through verification.
5. Helper resolves and launches the authoritative active app and waits for IPC readiness.
6. Success/no-op clears the terminal and shows only the final state; failure retains logs. The helper stays alive until the window is closed.

## Test and release gates

The design is accepted only if unit/platform menu tests, origin/lifecycle fixtures, full local gates, exact candidate, same-SHA main, immutable publication, fresh-public-byte lanes, production site, and installed Windows proof all pass. A tag is never created to rescue a failing candidate.

## Assumptions and confidence

- Tested: a separate helper is required to avoid lifecycle deadlock. Confidence: high.
- Tested: current updater must remain the sole mutation authority. Confidence: high.
- Open until platform tests: each menu can launch its terminal route without blocking its event loop. Confidence: high.
- Open until lifecycle fixtures: every failure-after-stop path can re-resolve and restart the authoritative active app. Confidence: medium.
- Open until physical/public proof: terminal clearing/retention and Windows installed UX match the intended experience. Confidence: medium.

## Sanity check

The design directly removes manual command entry while preserving the updater invariants that fixed the v1.3.3 permission defect. The strongest dissent is that a silent native helper would look more polished; it was rejected for this patch because cross-platform authentication and failure visibility would require three additional UI/result systems. Most likely failure mode: relaunch resolution after a partially successful installer; the typed outcome plus receipt-owned resolver and failure fixtures are therefore release-blocking.

Exit state: Directed. Next action is shared helper implementation, then three native adapters and staged lifecycle proof.
