# Goose v1.11.2 readiness

## Scope and preserved release

Task #g15 and [ADR 0057](../adr/0057-current-login-startup-installer-selection.md) correct
Windows installer startup choices. Fresh installation remains default-off. Upgrades and
repairs must respect the current choice after settings changes, with explicit installer
choices and unrelated options preserved. MSI and EXE changes cover both editions and both
architectures. Published v1.11.1/tag/47 assets remain unchanged.

## Original failure and containment

The official installed v1.11.1 Global MSI update succeeded after the operator approved the
fresh administrator prompt. Identity, icons, all four settings routes and isolated public
scrolling passed. Configuration preservation then failed: startup changed from false to
true although the operator did not change it. The official revision-safe settings service
restored false, removed the owned Run value, and recovered the exact original config hash
`7b31f4af277aa668c67be6778dd6a54f930635a68aa717c5da14ef5a0b6ec376`.
Local evidence is retained under `target/v1.11.1-installed/retry-20261019-182649/`.

[CI 39343205145](https://github.com/RealEmmettS/goose/actions/runs/39343205145) reproduces
the precise defect in both Global and Corporate MSI using public v1.11.0/v1.11.1 bytes:
fresh off; explicit on; app off; passive upgrade restores Run while receipt remains false;
settings read changes the config to true. The full MSI logs and five state snapshots are
retained in the two startup-regression artifacts and `target/startup-regression-red/`.
Those two failed checks are the preserved regression oracle, not release qualification.

## Local implementation checks

Rust formatting, strict workspace Clippy, the full workspace tests and the release build pass.
Settings tests, strict checks and the real optimized native build pass. Both x64 MSI packages
and both Inno Setup 6 packages compile with the startup correction. The C action passes the
compiler's warnings-as-errors check and PE architecture verification. These local package
compiles prove source/toolchain compatibility; the CI matrix qualifies exact packaged payloads.
The local ARM64 C cross-compile lacks the ARM64 CRT library, so it is not a passing ARM result;
the existing CI toolchain installation and native ARM64 lanes retain that gate.

The native matrix includes fresh default-off, both directions of app/installer drift, explicit
choices, unrelated selections, repair, foreign-command/type refusal, and a deferred MSI rollback
probe that records the changed Run value and new slot after activation before failing. The x64 MSI lanes additionally drive
the unmodified full wizard's startup selections and Maintenance Repair. None of these new native
cases is claimed passed until its runner completes successfully.

The first corrected-package run, [39345052402](https://github.com/RealEmmettS/goose/actions/runs/39345052402),
stopped before installer tests because three native settings version declarations still named
the prior patch. The declarations were aligned with Cargo/package metadata; the failed logs
remain preserved. Ordinary settings builds alone had not exercised this package-identity gate.

The corrected package run, [39345579125](https://github.com/RealEmmettS/goose/actions/runs/39345579125),
built both architectures and passed the existing native overlay/lifecycle/takeover checks.
All four EXE startup lanes passed eighteen state checks each. MSI stopped at a harness
type error: COM calls emitted null pipeline results around the feature-state integer.
Suppressing those outputs let both x64 editions pass the core startup states in
[39347134269](https://github.com/RealEmmettS/goose/actions/runs/39347134269).

Subsequent private rollback probes exposed two additional harness defects before they reached
the intended deferred failure: unreleased MSI view handles locked the copied database, and a
single-element argument list became a string when probe options were appended. A local private
file reproduction confirmed the old handle code retained the lock and the corrected code released
it, without invoking an installer. Both failed histories and their MSI logs remain preserved.
Diagnostic runs reuse the recorded package artifacts and report the harness revision, workflow
revision and installed receipt commit separately. They do not replace final unchanged-source
qualification. A subsequent maintenance probe reached Windows Installer source recovery, which
used the cached unmodified package and rejected the renamed source. The fixture now exercises
an actual predecessor-to-candidate upgrade in each startup state, retaining the original MSI
basename in its private directory. The probe is placed after slot activation and before finalization,
with its sequence derived and checked against the package. It requires the opposite Run state and
candidate version/commit during the failed transaction and exact original receipt/configuration afterward.

The first upgrade probe also revealed that a removal-only feature list on an uninstalled product
selects no application files and is treated as removal. Upgrade fixtures now select the required
Binaries feature explicitly in both directions. Each modified private MSI receives its own package
code, as required by [Windows Installer package identity rules](https://learn.microsoft.com/en-us/windows/win32/msi/package-codes).

[39348930598](https://github.com/RealEmmettS/goose/actions/runs/39348930598) passes both rollback
directions in both MSI editions, including actual opposite Run state and candidate version/commit
after activation, followed by exact original receipt/configuration restoration. The subsequent
wizard timed out at its welcome page because Windows exposed its named buttons as generic UI
Automation panes. The harness now uses those observed names and an owned-window click fallback;
the original feature-selection and repair assertions remain required.

The wizard diagnostics identified two independent automation-provider limitations.

with exact installer ownership, selected feature, popup focus, visible nonoverlapping contained
bounds and invocation support. It saves the screen before selecting Local or Absent and retains
the unchanged final startup/receipt/configuration assertions. No user-desktop installer tests ran.
